# API профиля — РК2

Предлагаемый контракт для фронтенда и бэкенда. Чтение пользователя уже есть;
сохранение профиля и загрузка аватара будут реализованы на бэкенде позже.

В этом документе описаны просмотр профиля, изменение имени и аватара.

## Пользователь

```json
{
    "id": "9f2c1b7e-4d3a-4f81-9c2e-5a7b3d0e1f46",
    "email": "andrey@example.com",
    "display_name": "Андрей",
    "avatar_url": null
}
```

`id` — строка, `avatar_url` — доступный браузеру абсолютный HTTP(S)-адрес
изображения или `null`, если аватара нет. Пароль и его хеш в ответ не входят.

## Чтение профиля

`GET /api/v1/auth/me` — существующий запрос без тела.

- `200` — объект пользователя.
- `401 unauthorized` — сессии нет или она истекла.
- `500 internal_error` — ошибка сервера.

После сохранения этот запрос должен возвращать новые имя и аватар,
в том числе после перезагрузки страницы.

## Сохранение профиля

`PATCH /api/v1/users/me` — новый запрос, пока не реализован.

Тело — `multipart/form-data`. Имя и выбранная фотография отправляются одной формой.

| Поле           | Тип    | Правило                                                    |
| -------------- | ------ | ---------------------------------------------------------- |
| `display_name` | строка | Обязательно; после обрезки пробелов по краям 2–50 символов |
| `avatar`       | файл   | Необязательно; JPEG или PNG                                |

Длину имени считаем в символах Unicode, как при регистрации. Если файл не передан,
сервер сохраняет прежний аватар. Пустое имя не означает «оставить прежнее»:
это ошибка валидации. Удаление аватара этим запросом не предусмотрено.

Пользователь определяется по сессии. Клиент не передаёт `id`, email или пароль.
Запрос не меняет email, пароль и сессию.

Фронтенд использует `FormData` и `credentials: 'include'`. Заголовок
`Content-Type` вручную не задаётся: браузер добавляет его вместе с `boundary`.
Текущее правило общего API о JSON-теле к этому запросу не применяется.

Сервер проверяет содержимое изображения, а не только расширение и MIME-тип файла.

### Успех

`200 OK`, тело — полный объект пользователя в том же формате, что у `/auth/me`.

Сервер возвращает успех после сохранения всех переданных изменений. Если он
возвращает ошибку валидации или сохранения, профиль не должен остаться обновлённым
частично: только имя или только аватар.

При замене фотографии возвращается новый URL, чтобы браузер не показывал старую
картинку из кеша. Сохранённый аватар должен быть доступен после перезапуска сервера.

### Ошибки

Ответы имеют существующий JSON-формат `error.code` и `error.message`.
Ошибки полей передаются в `error.fields`.

| HTTP | `error.code`             | Причина                                   |
| ---- | ------------------------ | ----------------------------------------- |
| 400  | `invalid_multipart`      | Не удалось разобрать форму                |
| 400  | `validation_failed`      | Неверное имя, формат или содержимое файла |
| 401  | `unauthorized`           | Нет действующей сессии                    |
| 413  | `payload_too_large`      | Превышен серверный лимит размера запроса  |
| 415  | `unsupported_media_type` | Тело запроса не `multipart/form-data`     |
| 500  | `internal_error`         | Не удалось сохранить профиль или файл     |

Новые коды относятся к сохранению профиля и не меняют ошибки существующих запросов.

```json
{
    "error": {
        "code": "validation_failed",
        "message": "Проверьте правильность заполнения полей",
        "fields": {
            "display_name": "Имя должно содержать от 2 до 50 символов",
            "avatar": "Выберите изображение JPG или PNG"
        }
    }
}
```

В `fields` включаются только поля с ошибками. Внутренние пути файлов и ошибки БД
в ответ не попадают.

## Перед подключением бэкенда

Нужно согласовать максимальный размер файла и запроса, а также способ CSRF-защиты
и необходимые для неё заголовки. Эти детали пока не определены существующим API;
фронтенд и бэкенд должны использовать одинаковые правила.
